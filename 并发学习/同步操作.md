
# 条件变量


`std::condition_variable` 和 `std::condition_variable_any`之间的区别在于配合什么锁使用

```cpp
std::mutex mtx;
std::condition_variable cv;
bool arrived = false;

void wait_for_arrival() {
    std::unique_lock<std::mutex> lck(mtx);
    cv.wait(lck, []{ return arrived; }); // 等待 arrived 变为 true
    std::cout << "到达目的地，可以下车了！" << std::endl;
}

void simulate_arrival() {
    std::this_thread::sleep_for(std::chrono::seconds(5)); // 模拟地铁到站，假设5秒后到达目的地
    {
        std::lock_guard<std::mutex> lck(mtx);
        arrived = true; // 设置条件变量为 true，表示到达目的地
    }
    cv.notify_one(); // 通知等待的线程
}
```

`std::condition_variable`的`wait()`一般搭配`std::unique_lock<std::mutex>`使用

这是因为`cv.wait(lock)`内部会做这样的事：
```
① 当前拥有 mutex
② wait() 临时 unlock()
③ 当前线程睡眠
④ 其他线程修改 arrived
⑤ 其他线程 notify_one()
⑥ 当前线程醒来
⑦ wait() 再次 lock()
⑧ wait() 返回
```

那么`wait()`需要一个可以`lock()`和`unlock()`的锁对象

`condition_variable_any`就宽泛的多 各种满足要求的锁都可以 包括自己写的锁类型

**注意：`std::condition_variable`和`std::condition_variable_any`不负责保护数据** `mutex`才负责互斥 这两个负责的是检查条件是否满足

## 条件变量的`wait()`成员函数

这个有两个版本

### 只传`unique_lock()`

```cpp
std::unique_lock<std::mutex> lock(mtx);

cv.wait(lock);
```

释放`mutex`后 线程睡眠 等到再收到`notify`后 重新获取`mutex` 最后`wait`返回

不过 考虑到[虚假唤醒](https://en.wikipedia.org/wiki/Spurious_wakeup)这个问题 我们需要手动判断`!arrived`

### 传入`unique_lock`和条件

```cpp
cv.wait(lock, [] {
    return arrived;
});
```

第二个参数叫做谓词 本质上就是返回一个`bool`

等价于
```cpp
while (!arrived)
    cv.wait(lock);
```

### 源码

```cpp
void wait(unique_lock<mutex>& _Lck) noexcept {
    _Cnd_wait(_Mycnd(), _Lck.mutex()->_Mymtx());
}

template <class _Predicate>
void wait(unique_lock<mutex>& _Lck, _Predicate _Pred) {
    while (!_Pred()) {
        wait(_Lck);
    }
}
```

可以从源码中显然看到 第二个版本是对第一个的包裹 并调用了第一个的重载

## 小细节

再回到原来的那个例子 注意到`simulate_arrival()`函数中间部分有一个`{}`

这是因为：
1. [[RAII]]
   在`{}`内部定义的`std::lock_guard<std::mutex>lck(mtx)`会在进入该作用域时对互斥量 `mtx` 加锁 当代码执行到该作用域的右花括号 `}` 时 `lck` 变量的生命周期结束被自动析构，从而**立即解锁 `mtx`**

2. 性能开销
   如果不用`{}` 则有可能`cv.notify_one（）`被调用时`mtx`仍处于加锁状态 会造成阻塞 需要等到函数完全退出才能释放这个锁 造成性能额外开销


# `future`

`future`是异步编程中用来代表“未来某个时刻才会准备好”的计算结果的凭证或对象

`std::future`和`std::shared_future`的关系就和`std::unique_ptr`和`std::shared_ptr`一样


## 异步任务的处理方式

一般分为三种：`std::async` `std::packaged_task` `std::promise` 
分别对应 最高层API 中层打包器 和 底层通道

这三者的实现底层全都基于一个共同的核心机制：共享状态（Shared State）

`std::future` 充当的是读取端（消费者） 而 `std::async` `std::packaged_task` 和 `std::promise` 充当的是写入端（生产者） 它们内部都是通过“共享状态”来进行跨线程的数据传递和同步的

### `std::async`

```cpp
#include <iostream>
#include <thread>
#include <future> // 引入 future 头文件

int task(int n) {
    std::cout << "异步任务 ID: " << std::this_thread::get_id() << '\n';
    return n * n;
}

int main() {
    std::future<int> future = std::async(task, 10);
    std::cout << "main: " << std::this_thread::get_id() << '\n';
    std::cout << std::boolalpha << future.valid() << '\n'; // true
    std::cout << future.get() << '\n';
    std::cout << std::boolalpha << future.valid() << '\n'; // false
}
```

`std::async`启动一个异步任务 返回一个`std::future`对象 这个对象持有结果 当我们调用`get()`的时候 如果后台任务还没算完 主线程就会在这里阻塞等待 直到任务完成并返回结果

`valid()`函数检查`future`是否关联当前共享状态 （如果调用`get()` `set()`都会返回`false`）

`std::async`的参数传递与`std::thread`完全一样 参见[[线程#线程参数的传递]]
即默认按值复制 需要引用时必须显示使用`std::ref`

核心原因也一样 是因为涉及到底层c风格API的传递 参考[[thread的源码解析]]
 
 `std::async`的执行策略有两种：`std::launch::async`在不同的线程上执行异步任务 `std::launch::deferred` 惰性求值 不创建线程 等待 `future` 对象调用 `wait` 或 `get` 成员函数的时候执行任务

如果不给出这个参数 `std::async`的调用策略就是`std::launch::async | std::launch::deferred` 由系统根据具体情况选择


#### 两个问题

A 
```cpp
std::async(std::launch::async, []{ f(); }); // 临时量的析构函数等待 f()
std::async(std::launch::async, []{ g(); }); // f() 完成前不开始
```

照 C++ 标准，临时对象的生命周期严格局限于**包含它的完整表达式（Full Expression）的结尾** 所以 当本行代码结束时 这个临时`future`的析构函数就会被立刻调用 

同时 C++ 标准对`std::async`返回的默认`future`析构函数做了一个特殊规定：**如果它还关联着一个正在运行的异步任务，析构函数会阻塞等待该任务执行完毕** 

因此 第一行代码必须等 `f()` 完全跑完 临时`future`析构结束 程序才会往下走去执行第二行 这导致它变成了“串行阻塞执行” 完全失去了异步的意义

但是如果使用具体变量名`f1` `f2`时其生命周期会延续到当前作用域的末尾 离开作用域时会按照构造的相反的顺序析构 但不影响这两个任务在后台已经并行跑完了


B
```cpp
auto t = std::async([] {});
std::future<void> future{ std::move(t) };
t.wait();   // Error! 抛出异常
```

`std::future`被移动后没有选择权 失去了共享状态 所以就不能调用`get()` `wait()`这些成员函数

这个就和`std::thread`一样 参见[[线程#`std thread`转移所有权]]


### `std::packaged_task`

一句话简单理解：`std::packaged_task`只负责把函数包装起来 而什么时候、在哪执行由自己决定

`std::packaged_task`负责包装任何可调用对象

```cpp
std::packaged_task<double(int, int)> task([](int a, int b){
    return std::pow(a, b);
});
std::future<double>future = task.get_future();
task(10, 2); // 此处执行任务
std::cout << future.get() << '\n'; // 不阻塞，此处获取返回值
```

不过需要注意的是 `std::packaged_task`只能执行 但不能获得返回值 所以就必须与`future`关联 然后使用`future.get()`来获得返回值

同样的 我们也可以把这个放在另一个线程中来执行 如：
```cpp
std::packaged_task<double(int, int)> task([](int a, int b){
    return std::pow(a, b);
});
std::future<double> future = task.get_future();
std::thread t{ std::move(task),10,2 }; // 任务在线程中执行
// todo.. 幻想还有许多耗时的代码
t.join();

std::cout << future.get() << '\n'; // 并不阻塞，获取任务返回值罢了
```

### `std::promise`

简单理解：`promise`是往共享状态写结果的一端 `future`是从共享状态取结果的一端

```cpp
// 计算函数，接受一个整数并返回它的平方
void calculate_square(std::promise<int> promiseObj, int num) {
    // 模拟一些计算
    std::this_thread::sleep_for(std::chrono::seconds(1));

    // 计算平方并设置值到 promise 中
    promiseObj.set_value(num * num);
}

// 创建一个 promise 对象，用于存储计算结果
std::promise<int> promise;

// 从 promise 获取 future 对象进行关联
std::future<int> future = promise.get_future();

// 启动一个线程进行计算
int num = 5;
std::thread t(calculate_square, std::move(promise), num);

// 阻塞，直到结果可用
int result = future.get();
std::cout << num << " 的平方是：" << result << std::endl;

t.join();
```

所以 我们要显式的进行`set_value()`和 进行与`future`关联后的`get()`


除了`set_value()`之外 还有一个`set_exception()` 它接受一个 [`std::exception_ptr`](https://zh.cppreference.com/w/cpp/error/exception_ptr) 类型的参数 这个参数通常通过 [`std::current_exception()`](https://zh.cppreference.com/w/cpp/error/current_exception) 获取 用于指示当前线程中抛出的异常

`future`可以通过`get()`获得这个异常

如：
```cpp
void throw_function(std::promise<int> prom) {
    try {
        throw std::runtime_error("一个异常");
    }
    catch (...) {
        prom.set_exception(std::current_exception());
    }
}

int main() {
    std::promise<int> prom;
    std::future<int> fut = prom.get_future();

    std::thread t(throw_function, std::move(prom));

    try {
        std::cout << "等待线程执行，抛出异常并设置\n";
        fut.get();
    }
    catch (std::exception& e) {
        std::cerr << "来自线程的异常: " << e.what() << '\n';
    }
    t.join();
}
```

注：`async` `packaged_task` `promise` 都可以存储和传递异常 不过前两者都是自动的（包装好的） 而`promise`是要我们去手动控制的


### 三者对于复制和移动的态度

简单来说 `std::packaged_task` `std::promise`都只能移动 不能复制

而`std::async`是一个函数 所以我们关心的是传进去的对象和参数

这个在[[同步操作#`std async`]]中提到了

为什么不能复制 这个大致和`thread` `mutex`差不多 参见[[线程]] [[mutex]]


## `future`的状态变化

一句话：`future`是一次性的

移动语义：因为**移动操作标志着所有权的转移** 意味着`future`不再拥有共享状态 `get`和`wait`函数要求`future`对象拥有共享状态 否则会抛出异常

共享状态失效：调用 `get` 成员函数时 `future`对象必须拥有共享状态 但调用完成后 它就会**失去共享状态** 不能再次调用 `get`

源码：

```cpp
// std::future<void>
void get() {
    // block until ready then return or throw the stored exception
    future _Local{_STD move(*this)};
    _Local._Get_value();
}
// std::future<T>
_Ty get() {
    // block until ready then return the stored result or throw the stored exception
    future _Local{_STD move(*this)};
    return _STD move(_Local._Get_value());
}
// std::future<T&>
_Ty& get() {
    // block until ready then return the stored result or throw the stored exception
    future _Local{_STD move(*this)};
    return *_Local._Get_value();
}
```


为什么要先通过`_STD move(*this)` 把当前的 `future` 对象（即 `this`）移动到一个局部临时对象 `_Local`中？

这样子会使原来的`this`对象失去所持有的共享状态 即调用完`get()`后 `valid()`会变为`false`

而同时 局部对象`_Local`在函数结束时析构 这意味着当前对象失去共享状态 并且状态被完全销毁
这样子可以及时清理内存

这也就解释了为什么只能调用一次`get()`


## `std::shared_future`

如果多个线程需要异步任务的返回值 而`future`的`get()`只能调用一次 那我们就需要用 `std::shared_future` 来替代 `std::future`

`std::shared_future`是可复制的 多个对象可以指代同一个共享状态

所以我们可以创建多个副本来确保线程安全

```cpp
std::string fetch_data() {
    std::this_thread::sleep_for(std::chrono::seconds(1)); // 模拟耗时操作
    return "从网络获取的数据！";
}

int main() {
    std::future<std::string> future_data = std::async(std::launch::async, fetch_data);

    std::shared_future<std::string> shared_future_data = future_data.share();

    std::thread thread1([shared_future_data] {
        std::cout << "线程1：等待数据中..." << std::endl;
        shared_future_data.wait();
        std::cout << "线程1：收到数据：" << shared_future_data.get() << std::endl;
    });

    std::thread thread2([shared_future_data] {
        std::cout << "线程2：等待数据中..." << std::endl;
        shared_future_data.wait();
        std::cout << "线程2：收到数据：" << shared_future_data.get() << std::endl;
    });

    thread1.join();
    thread2.join();
}
```


# C++20 闩 (latch) 与屏障 (barrier)

## [`std::latch`](https://mq-b.github.io/ModernCpp-ConcurrentProgramming-Tutorial/md/04%E5%90%8C%E6%AD%A5%E6%93%8D%E4%BD%9C.html#std-latch)

一句话：**减少**计数，**无法增加计数** 

通过调用`wait`函数阻塞子线程 直到主线程调用`count_down`函数原子地将计数减至`0` 从而解除阻塞

```cpp
std::latch latch{ 10 };

void f(int id) {
    //todo.. 脑补任务
    std::this_thread::sleep_for(1s);
    std::cout << std::format("线程 {} 执行完任务，开始等待其它线程执行到此处\n", id);
    latch.arrive_and_wait();
    std::cout << std::format("线程 {} 彻底退出函数\n", id);
}

int main() {
    std::vector<std::jthread> threads;
    for (int i = 0; i < 10; ++i) {
        threads.emplace_back(f,i);
    }
}
```

[`arrive_and_wait`](https://zh.cppreference.com/w/cpp/thread/latch/arrive_and_wait) 函数等价于：`count_down(n); wait();`


## `std::barrier`

和`std::latch`差不多 但是可以反复使用

```cpp
std::barrier barrier{ 10,
    [n = 1]()mutable noexcept {std::cout << "\t第" << n++ << "轮结束\n"; }
};

void f(int start, int end){
    for (int i = start; i <= end; ++i) {
        std::osyncstream{ std::cout } << i << ' '; 
        barrier.arrive_and_wait(); // 减少计数并等待 解除阻塞时就重置计数并调用函数对象
        
        std::this_thread::sleep_for(300ms);
    }
}

int main(){
    std::vector<std::jthread> threads;
    for (int i = 0; i < 10; ++i) {
        threads.emplace_back(f, i * 10 + 1, (i + 1) * 10);
    }
}
```


lambda 表达式必须声明为 `noexcept` ，因为 `std::barrier` 要求其**函数对象类型必须是不抛出异常的**

如果能抛异常 那么会有以下问题：

barrier 当前阶段怎么算？
其他等待线程怎么办？
新的阶段是否开始？

所以就直接要求不抛异常
